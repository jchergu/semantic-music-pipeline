# 7. Live Demonstration

Chapters 5 and 6 describe each use case from the inside: its modules, its evaluation harness, its measured results, all reported for a reader working through source code and API responses. This chapter is deliberately different in kind, added in response to feedback that a thesis demonstrating three concrete use cases should show them at work through an interface built for the person who would actually use a music application, not only through the technical record the preceding two chapters already give. Three small web dashboards (`demo/`), one per use case, drive the real running stack live: the same Semantic API, session API, and proactive service the rest of this thesis measures, called from a browser over HTTP and WebSocket rather than replayed from a recording. Nothing shown below is staged -- every screenshot is a live capture against the same running example introduced in Section 1.3, the three-track thread "Gates" (#14, Bellevue) to "Billy Comes Home" (#15, Heifervescent) to "Give Me Hope" (#16, Modern Pitch).

Each section below carries two views of the same interaction, switched with a tab rather than shown as separate pages: an embedding-space scatter (a real 2D PCA projection of all 411 catalog tracks' 512-dimensional CLAP embeddings, `demo/precompute_embedding_space.py`) and a knowledge-graph view (a real force-directed layout of the Track/Artist/Genre nodes and edges the Semantic API's `/tracks/{id}/graph` endpoint returns from Neo4j, `demo/graph.js`). The two views are genuinely different evidence, not two renderings of the same fact: the scatter shows continuous similarity in the same embedding space Milvus searches, while the graph shows the discrete relational structure the ranking function's genre-sibling and same-artist signals are actually computed from. Two components explain only 22% of the embedding space's variance, so the scatter is a rough visual cue rather than an exact map; the graph has no such caveat; the KG edges it draws are exactly the edges the Semantic API returns.

## 7.1 Use Case 8.1: Batch, Reactive

The seed track is "Gates," queried live against `usecases/8_1_batch_reactive/demo_api.py` -- a thin wrapper around the same `context_builder.build_context()` and `ranking.score_recommendations()` functions Section 5.6.1 already describes, called here over HTTP instead of run as a batch, computing nothing Chapter 5's own recommender does not already compute.

![Figure 7.1: 8.1's demonstration page, embedding-space view, live against the running example. Left: the seed track "Gates" (blue, ringed) plotted against a real PCA projection of all 411 catalog embeddings, connected to its top-10 recommendations (gold) as they're computed. Right: the same ranked list, with a per-row breakdown of which of the three signals -- CLAP similarity, genre-sibling status, same-artist status -- contributed to each score.](figures/fig-7-1-uc81-demo-scatter.png){width=6.3in}

The top result, "Give Me Hope," is both acoustically similar to "Gates" (CLAP cosine 0.843) and a genre sibling -- the two signals stacking, exactly as Section 5.6.1's additive scoring is designed to do. This is not a separate code path built for the screenshot: the demo endpoint calls the same functions over the same frozen Semantic API contract of Section 5.6.3. Section 7.2 continues this exact thread -- "Gates," "Billy Comes Home," and "Give Me Hope" playing in sequence -- to show what changes once the same three signals are computed over a *session* instead of a single seed.

![Figure 7.2: 8.1's demonstration page, knowledge-graph view, same seed and recommendations as Figure 7.1. Each shown track's real artist (violet) and genre (teal) edges from Neo4j, plus, dotted, up to five further genre-sibling tracks from the same query the ranking function draws on. The dense cluster around "Gates" is the same genre-sibling/same-artist structure Figure 7.1's badges report as scores, here as the graph they are actually computed from.](figures/fig-7-2-uc81-demo-graph.png){width=6.3in}

The secondary pair from Section 1.3 makes the same-artist signal concrete in a way this rock thread cannot, since none of its three tracks share an artist. Querying "Wish You Were Here" (#1, The.madpix.project) returns "Moments" (#12, the same artist) in first place, with a raw CLAP similarity of only 0.458 -- lower than the second-ranked candidate's 0.584. The genre-sibling and same-artist boosts (0.05 and 0.15) together outweigh that gap, exactly the re-ranking behaviour Section 5.6.1 describes boosts existing for: pulling a track the acoustic signal alone would have placed lower into the top spot, on the strength of a high-precision structural signal a purely content-based comparison cannot see. On the knowledge-graph view this same fact is a single shared artist node connecting both tracks directly, rather than a badge computed from one.

## 7.2 Use Case 8.2: Streaming, Reactive

This section shows the same pipeline running against the running example, continuing directly from Section 7.1: the same three tracks, "Gates," "Billy Comes Home," and "Give Me Hope," played in sequence as one session rather than queried one at a time.

![Figure 7.3: 8.2's demonstration page, embedding-space view, live against the running example. Left: the session's three played tracks (blue, connected in play order) against the same real PCA projection Figure 7.1 uses, with the session's centroid position (green) and its resulting recommendations (gold) connected to it. Right: session state, showing a computed 512-dimensional profile from three events (the Flink job of Section 6.1.4 has already fired a window), and the ranked list itself, computed by the warm path of Figure 6.3 over the session profile rather than over any single track. The centroid marker's position is the mean of the three played tracks' own 2D positions, a visual approximation for this scatter -- not a projection of the real 512-dimensional weighted centroid, which lives in a space this 2D view cannot show exactly.](figures/fig-7-3-uc82-demo-scatter.png){width=6.3in}

The list this session returns is not the list Figure 7.1 returned for "Gates" alone: "When the Stars Fall from Grace" now ranks first, a track that appeared nowhere in Section 7.1's single-seed result. This is the cold-start-to-warm handoff of Figure 6.2 made visible on one concrete example: querying "Gates" in isolation and playing "Gates" as the opening track of a session that continues through "Billy Comes Home" and "Give Me Hope" are different inputs to the same scoring function, and Section 6.1.5's warm path is what makes the second one session-aware rather than seed-aware. Reaching this state on the live stack required exactly what Section 6.1.5 describes: the raw-state daemon caching three events, the Flink job's window firing once enough event time had passed, and the refresh daemon's debounce re-evaluating on a subsequent event and finding a profile where its previous refresh had found none -- the race Figure 6.2 describes, observed rather than staged.

![Figure 7.4: 8.2's demonstration page, knowledge-graph view, same session as Figure 7.3. All three played tracks' real artist and genre edges drawn on one graph -- the shared "rock"/"pop"/"indie" genre nodes and the partially-overlapping artist set across "Gates," "Billy Comes Home," and "Give Me Hope" make visible, structurally, the same taste continuity the profile centroid captures numerically in Figure 7.3.](figures/fig-7-4-uc82-demo-graph.png){width=6.3in}

## 7.3 Use Case 8.3: Streaming, Proactive

Everything in Sections 6.2.3-6.2.7 is a design; the minimal real slice built to show that design running end-to-end continues the running example: "Give Me Hope," the last track of the same three-track session Sections 7.1 and 7.2 already used.

![Figure 7.5: 8.3's demonstration page, embedding-space view, live against the running example. Left: "Give Me Hope," the currently-playing track, highlighted on the same catalog projection Figures 7.1 and 7.3 use, connected live to the pushed suggestion the moment it is computed. Right: the live classifier's top-3 CLAP zero-shot tags (artrock/country/poprock) are a real, imperfect result on this small amateur catalog, not a cherry-picked one; the pushed suggestion is the same-artist, genre-sibling, high-similarity track the batch signals of Chapter 5 already favour.](figures/fig-7-5-uc83-demo-scatter.png){width=6.3in}

The suggestion in Figure 7.5 illustrates why this is a demonstration and not an evaluation. It is a strong result on this one example -- the same artist, a genre sibling, and 0.854 cosine similarity all agreeing -- but one example is not a sample, and the live classifier's own top-3 tags are visibly imperfect (an art-rock/country/pop-rock reading of a track catalogued as rock/pop/indie). This is a real, unhidden observation about applying a general-purpose zero-shot classifier to a small, amateur catalog, consistent with Section 3.2's note that CLAP's training distribution is general-purpose rather than music-specific -- but it is one example, not a measurement, and no accuracy claim is made from it. Neither observation is a finding; both are exactly what Section 6.2.2 predicts a demonstration can and cannot show.

![Figure 7.6: 8.3's demonstration page, knowledge-graph view, same moment as Figure 7.5. Solid edges are the real catalog graph: "Give Me Hope"'s true artist and genre nodes. Dashed orange edges are the live classifier's own top-3 zero-shot tags, drawn on the same graph specifically to make the gap between prediction and ground truth visible rather than hidden -- two of the three predicted tags (country, poprock) are not among the track's three real catalog genres (pop, rock, indie), while the pushed suggestion (green) sits correctly inside the real genre-sibling structure regardless.](figures/fig-7-6-uc83-demo-graph.png){width=6.3in}

What Figures 7.5 and 7.6 together demonstrate is narrower and more defensible than an evaluation would claim: that the design of Sections 6.2.3-6.2.4 is not merely proposed, it runs, on real data, against the same pipeline Section 6.1 measured, and that the classifier's real limitations are visible on the same page as its results rather than reported only in prose.
